SQL 처리 흐름
1. 구문 분석
- 사용자가 요청한 SQL문이 데이터베이스에서 처음 사용된 문장인지, 이미 사용한 문장인지를
공유 풀 영역을 검색하여 확인

* 공유 풀 영역
- ㄴSQL 실행 계획을 저장하는 메모리 영역(SQL문이 보관되어 있다.)

사용된 적 있는 문장 -> 공유 풀에서 꺼내서 쓰면 됨(구문분석 필요 x)
처음 사용되었다 -> 구문분석을 실시

구문분석
-  SQL문을 데이터베이스가 이해할 수있도록 분석하는 작업
예시 
SELECT문법이 올바른가
MEMBER 테이블이 존재하는가
NAME 컬럼이 존재하는가
MEMBER_ID 컬럼이 존재하는가 
사용자가 MEMBER 테이블을 조회할 권한이 있는가?

- 옵티마이저는 SQL문을 가장 빠르게 데이터를 검색해줄 수 있는 실행 계획을 갖는다.

* 옵티마이저 
- SQL을 가장 효율적으로 실행할 방법을 결정하는 데이터베이스 내부 기능이다.

2. 실행
- 구문 분석이 끝난 SQL을 실제로 실행하는 단계
- 서버 프로세스는 메모리 영역의 데이터베이스 버퍼 캐시 영역을 검색하여
   해당 테이블의 데이터가 다른 사용자의 다른 SQL문에 의해 존재하는지 검색

* 데이터베이스 버퍼 개시
- 실제 테이블 데이터를 저장하는 영역

버퍼 캐시 영역에 있으면 그대로 사용

없으면 해당 테이블의 데이터파일에서 데이터를 잃고 버퍼캐시에 저장

INSERT UPDATE DELETE와 같은 문장이라면 데이터 버퍼 캐시 영역에서 
 새로운 데이터로 변경, 삭제 또는 입력을 한다.

3. 추출
실행 결과를 사용자에게 보내주는 단계
서버 프로세스는 데이터베이스 버퍼 캐시 영역에서 관련 테이블 데이터를 
  알아서 사용자가 요청한 클라이언트로 보내준다.

SELECT 문을 실행하는 경우에만 추출단계가 실행된다.

SQL 작성시 고려사항 
- 개발자가 SQL 특성을 충분히 이해하여 SQL문을 적절히 구사할 수 있는 능력을 갖춰야 한다.
- 사용자가 SQL 작성시 옵티마이저가 실행 계획을 수립한 후 실행되는 일련의 과정을 이해하고 작성해야 한다.
- 구문분석 단계 시 옵티마이저가 수립한 실행 계획에 따라 엄청난 수행 속도 차이가 발생할 수 있다.
- 특정 SQL이 실행될 떄 옵티마이저에 의해 수립된 실행 계획은 제어하기 어렵지만 옵티마이저가 비정상적으로
   동작한다면 이를 주기적으로 개발자가 원하는 실행 계획으로 동작될 수 있도록 조정하는 과정이 필요하다.
- 개발자는 옵티마이저가 정상적인 실행 계획을 수립할 수있도록 종합적이고 전체적인 포인트를 SQL에 부여하여 작성해야 한다.
- 좋은 SQL은 추출되는 결과를 추론하여 SQL을 집합적으로 접근하여 작성해야 한다.

EXPLAIN PLAN의 활용
- 사용자들이 SQL문의 액세스 경로를 확인하여 성능 개선을 할 수있도록 SQL문을 분석하고
   해석하여 계획을 수립하고, 관련 테이블에 저장하도록 지원해주는 도구

테이블 조작 프로시저 성능 개선하기
1. 분석가에 의해 정의된 유가사항을 시준으로, 성능, 측정 도구를 활용하여
    조작 프로시저의 성능을 측정한다.
- 응답시간, 처리건수 , 리소스사용량 등을 목표로 분석하고 테스트 대상 성능 기준을 정의한다.
- 성능 도구 설정, Trace로그, 수집 준비
-테스트용 데이터를 사용하여 프로시저 실행하고, 실행결과 및 Trace 로그 수집
- 결과를 분석하여 지표를 검토한다.
2. 실데이터를 기반으로 텍스트를 수행하여 데이터 조작 프로시저의 성능에 영향을 주는 병목구간을 파악한다.
-운영데이터의 복사본 또는 유사 데이터를 준비하여 성능 데이터 시나리오 작성
- pl/sql블록 실행 또는 SQL ㄴㅊ갸ㅔㅅ 반복실행을 통해 성능 데이터 수집
- 병목지점 식별
- 성능 저하 원인 보고서 작성
3, 테스터 결과와 정의된 요구사항을 기준으로 데이터 조작 프로시저의 성능의 따른 이슈를 해결한다.
- 속도를 저하시키는 sql 구문을 재작성하여 성능을 개선한다.
- 실행 계획을 개선한다,
- 인덱스를 재구성한다.
- 시스템 리소스 병목 구간을 조정한다.
- 개선 후 동일한 테스트로 효과를 검증한다.
- 성능 개선 결과를 문서화 하고 공유한다.
