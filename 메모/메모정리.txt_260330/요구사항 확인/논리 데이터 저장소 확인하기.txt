엔티티 -> 테이블로 변환
ㄴ 일반적으로 테이블과 엔티티 명칭은 동일하게 하는것을 권고
속성 -> 컬럼으로 변환
ㄴ 속성의 명칭과 반드시 일치할 필요는 없으나, 개발자와 사용자 간의 의사소통을 위하여
       가능한 표준화된 언어를 사용하도록 한다.
ㄴ SQL 예악어 사용은 피해야한다.
ㄴ SQL 문장의 가독성을 높이기 위해 컬럼명칭은 가능한 짧은 것이 좋다.
UID -> 기본키(PK)로 변환
관계 -> 왜래키(FK)로 변환
ㄴ 외래키로 설정된 컬럼의 이름도 보통은 기본키쪽의 이름을 그대로 사용
컬럼 타입 및 길이를 정의
ㄴ 내가 넣은려는 데이터의 크기를 파악해서 컬럼의 길이를 지정

삭제할 떄 
- 참조된 기본키의 값이 삭제될 경우  어떻게 처리할지 정하는 규칙
고객이 삭제되면, 그 고객의 주문 데이터는 어떻게 할 것인가

CASCADE
- 부모테이블의 데이터가 삭제되면 , 그 데이터를 참도하고 있던 
   자식 테이블의 데이터도 함께 삭제되는 방식

FORDEIGN KEY (customer_id) REFERENCES customer(costomer_id)
ON DELETE CASCADE

RESTRICTED
- 자식데이터에서 사용중인 값이 있으면
 부모데이터를 삭제하지 못하도록 막는 방식

foreign key(sutomer_id) referencs custoner(customer_id)
on delete restrict

Nullify
- 부모데이터가 삭제되면 , 자식 테이블의 외래키 값을 NULL 로 바꾸어라
- 자식 테이블의 외래키 컬럼이 반드시 NULL을 허용해야 한다,

foreign key(sutomer_id) referencs custoner(customer_id)
on delete set null

수정할 떄 
CASCADE
- 기본키 내용이 수정되면 참조되는 외래키 값도 같이 수정되는 것
foreign key(sutomer_id) referencs custoner(customer_id)
on update cascade

RESTRICT
- 외래키로 참조되고 있으면 ㄱ비노키의 값을 수정하지 못하도록 막는다.
foreign key(sutomer_id) referencs custoner(customer_id)
on update restrict

Nullify
- 부모테이블의 기본키 값이 수정되면, 자식 테아블의 외래키 값을 NULL로 바꿈
foreign key(sutomer_id) referencs custoner(customer_id)
on update set null

인덱스 설계
- 데이터를 빠르게 찾기 위해 만드는 검색용 목차
 
인덱스 적용 기준
컬럼의 분포도가 10~15% 이내인 경우
분포도: 해당 컬럼의 값이 얼마나 다야하게 나뉘어 있는지 의미
분포도 : (1/컬럼의 도메인 갯수) x 100

회원번호 -> 모두가 다르다
10000

분포도 = (1/10000) x 100 = 0.01%

이런 컬럼은 인덱스 효과가 크다

10% 이하 : 점점 효율이 좋아진다.
10~15% :  일반적으로 사용할 수 있다
15% 이상으로 올라갈수록 : 인덱스 효율이 떨어짐

분포도 번위가 이상이더라도 부분 처리를 목적으로 하는 경우

orders
주문상태    건수
완료          90000
배송중       8000
취소          2000

실제 업무에서 자주  조회되는 데이터가 '취소' 2000건이라면 전체 2%만 조회함
- 이런 경우 부분처리를 목적으로 인덱스를 사용할 수 있음
- 단순히 값의 종류만 보지말고 실제 조회 조건에서 몇 건지 조회되는지 봐야한다.

조회 및 출력 조건으로 사용되는 컬럼인 경우
- 입출력 표나 화면 설계서에서 자주 검색 조건으로 사용되는 컬럼인 경우 

주문 
주문번호
회원ID
주문일자
주문상태

- 누가 언제 주문을 하는지 조회를 많이 한다면 회원ID랑 주문일자에 인덱스를 고려할 수도 있다.

기본키랑 UNIQUE 제약조건은 인덱스를 자동으로 생성한다.

인덱스 컬럼의 선정
- 분포도가 좋은 컬럼은 단독 인덱스로 생성한다.
분포도가 좋다는 것은 검색 결과가 적게 나오는 컬럼이라는 뜻

회원번호     이메일
1               a@test.com
2               b@test.com
3               c@test.com
4               d@test.com

인덱스는 보통 특정 컬럼에 조건을 걸 떄 사용된다.

select*
fromm user
where email = 'c@test.com';

CREATE INDEX idx_ussesr
ON users(email);

결합 인덱스를 사용하는 경우
- 조건이 여러개 걸릴 때

select*
from orders
where member_id = 10
and order_date >= '2026-01-01';

CREATE INDEX idx_member_id_order_date
on orders(member_id, order_date);

결합 인덱스는 컬럼 순서가 중요하다

수정이 빈번하지 않은 컬럼을 선정한다.
- 인덱스는 조회를 빠르게 해주지만, 삽입, 수정, 삭제 작업에는 부담이 된다.
- 인덱스로 선정한 컬럼의 정리 내용을 따로 저장을 하기 때문에 테이블 데이터가
   바뀔 떄 인덱스도 같이 바뀌어야 한다.

설계 시 고려사항
새 인덱스가 기존액세스 경로에 영향을 줄 수 있다.
- 액세스 경로 : DBMS가 데이터를 찾기 위해 선택한 이동 방법
대표적인 액세스 경로
1. FULL TABLES Scan(전체 테이블 검색)
- DB가 처음부터 끝까지 전부 읽는다.
2. Index Scan(인덱스 검색)
- 인덱스를 사용해서 필요한 위치만 바로 찾는다.

지나치게 많이 만들면 오버헤드가 된다.
오버헤드: 빠르게 찾기 위해 만든 목차가 너무 많아서 오히려 관리가 힘들어 지는 것
- 인덱스가 많으면 조회는 빨라질 수 있지만, 데이터 변경 작업은 느려진다.

인덱스는 추가 저장공간이 필요하다.
- 인덱스는 테이블과 별도로 저장되는 검색구조이다.
- 인덱스를 만들면 저장공간을 추가로 사용한다.

넓은 범위를 인덱스로 처리하면 오히려 느릴 수 있다.
- 적은 데이터를 빠르게 찾을떄 효과적이다.
- 하지만 전체 데이터의 많은 부분을 조회하면 오히려 전체 테이블을 읽는것이 더 빠를 수 있다.

인덱스와 테입르 데이터의 저장공간을 적절히 분리한다.
- 대규모 DB에서는 테이블 데이터와 인덱스 데이터를 물리적으로 분리해서 저장하기도 한다.

뷰(view) 설계
-select 한 결과를 테이블인것 처럼 저장하는 가상 테이블

뷰가 필요한 이유
복잡한 SQL을 단순하게 사용할 수 있다.
특정 컬럼만 보여줄 수 있다.
조건에 맞는 데이터만 보여줄 수 있다.

뷰 속성
REPLACE
뷰가 이미 존재하는 경우 기존 뷰를 새 내용으로 다시 생성하는 속성
CREATE OR REPLACE 뷰이름 AS
select문
MySQL & ORACLE 둘다 됨

FORCE
기본테이블이 존재하지 않아도 뷰를 생성하는 속성

ORACLE만 됨

- 뷰를 사용하려고 하면 에러가 발생할 수 있다.

NOFORCE
ORACLE에서만 사용가능 
- 참조하려는 테이블이 무조건 존재해야 뷰 생성 가능

WITH CHECK OPTION 
- 뷰의 조건을 만족하는 행만 INSERT, UPDATE할 수 있도록 제한하는 속성
- 원본 테이블이 아닌 뷰에다가 INSERT, UPDATE를 하는 것

CREATE VIEW 뷰이름 AS
SELECT..
WITH CHECK OPTION;

WITH READ ONLY
- 뷰를 조회 전용으로 만드는 속성이다.
- INSERT, UPDATE, DELETE는 불가능하다.
CREATE VIEW 뷰이름 AS
SELECT..
WITH READ ONLY;

뷰 설계시 고려 사항
뷰는 결국 테이블을 조회한다.
- 실제 데이터를 저장하지 않는다.
- 뷰는 내부적으로  SELECT문을 실행해서 결과를 보여준다.
- 그래서 뷰를 사용한다고 해서 무조건 빨라지는던 아니다
- 오히려 뷰 안의 SQL이 복잡하면 성능 문제가 생길 수 있다.

복잡한 뷰는 성능이 느려질 수 있다.
뷰 안의 SELECT문의 조건도 인덱스를 고려해야 한다.

파티션
-  하나의 큰 테이블을 내부적으로 여러 조각으로 나누어 저장하는 기술
- 겉으로는 하나의 테이블로 보여진다.

왜 파티션이 필요한가?
- 대용량 데이터를 여러 영역으로 나누어 저장함으로써, 조회 시 필요한 데이터만
  읽어 성능을 향상시키고 백업, 복구, 삭제 같은 관리 작업을 효율적으로 수행하기 위해 사용한다.

해쉬분할(Hash Partioning)
- 특정 컬럼 값을 계산(Hash)해서 데이터를 여러 구역에 균등하게 나누어 저장하는 방법

범위 분할의 경우 -> 사람이 직접 분할의 기준을 정한다.

2024년 -> p2024
2025년 -> p2025
2026년 -> p2026

해시분할은 DB가 직접 계산해서 자동으로 분배를 한다.

데이터 편중 문제
2024년에는 주문이 많았다. -> p2024 파티션에 너무 많은 데이터가 들어감
2025년에는 주문이 적다. 

해시 분할을 사용 

CREATE TABLE users(
       user_id INT,
       name VARCHAR(50)
)
PARTITION BY HASH(user_id)
PARTITONS 4;

DB는 내부적으로 해시값 % 파티션 개수 방식으로 계산을 한다.

1 % 4 = 1
2 % 4 = 2
3 % 4 = 3
4 % 4 = 0
5 % 4 = 1
6 % 4 = 2
7 % 4 = 3
8 % 4 = 0

데이터를 추가할 떄 특정 파티션에 추가하는게 아니라 DB가 자동으로 계산해서 저장한다.

해쉬분할의  장점
데이터 분산 : 특정 파티션에 데이터가 몰리는 현상을 감소시킨다.
저장 균형 : 여러 파티션 크기를 비슷하게 유지
특정 키 조회 빠름 : ID 기본 조회에 적합
대용량 처리 : 부하를 여러 파티션으로 분산할 수 있다.

해쉬분할의 단점
범위 조회에 약함 : 날짜 범위 검색 비효율
사람이 예측 어렵다 : 어느 파티션에 있는지 알기 어렵다.
파티션 개수 변경이 어렵다 : 재분배 작업이 발생할 수 없다.

조합 분할( Composite Partitioning)
- 파티션 기준으로 2개 이상 조합해서 데이터를 나누는 방식
- 먼저 큰 기준으로 한 번 나누고, 그 안에서 다시 작은 기준으로 한번 더 나누는 방식

orders 
ㄴ p2024 (2024년 주문) -> 1천만 개
ㄴ p2025 (2024년 주문) -> 1억개
ㄴ p2026 (2024년 주문) -> 1천만개 

연도별로 나누어도 p2025안에서는 여전히 데이터가 많다.
파티션 안에서 파티션을 한 번 더 나눈다.

1차 분할 : 주문일 기준 연도별 분할
2차 분할 : 고객번호 기준 해시 분할

CREATE TABLE orders(
        order_id INT,
        customer_id INT,
        order_date DATE
)
PARTITION BY RANGE(YEAR(order_date)) -> 주문일의 연도 기준으로 먼저 나눔
SUB PARTITION BY HASH (customer_id)
SUB PARTITIONS 4  -> 각 년도 파티션 안에서 고객번호를 기준으로 다시 4개로 나누겠다.


      PARTITION p2024 VALUES LESS THAN(2025),
      PARTITION p2025 VALUES LESS THAN(2026),
      PARTITION p2026 VALUES LESS THAN(2027),
) 

101, 11 , '2025-03-01'

1단계 : 연도 확인
YEAR('2025-03-01') = 2025

2단계 : 고객 번호
customer_id = 11

11 % 4 = 3

p2025의 세 번쨰 서브 파티션에 들어가게 된다.

      ㄴ sub3

조회할때 어떻게 동작할까?
- 연도 조건만 있는 경우
select *
from orders
where order_Date between '2025-01-01' and '2025-12-31';

2025년 파티션만 찾는다.
단, p2025 내부의 서브파티션은 여러개를 확인할 수 있다.

select*
from orders
where order_date between '2025-01-01' and '2025-12-31'
and customer_id = 11

p2025먼저 탐색 
고객번호가 들어있는 파티션만 탐색

조합 분할을 사용하는 이유
- 대용량 데이터 관리 : 1차 파티션만으로 부족할 떄 사용
- 조회 범위 축소 : 날짜 조건과 고객 조건을 함꼐 조회할 때 좋다.
- 데이터 분산 : 특정 연도나 월에 데이터가 올리는 문제를 줄일 수 있다.
- 관의 편의성 : 연도별 삭제, 백업 같은 작업을 하면서 내부 분산도 가능하다.

언제 사용하면 좋을까?
- 주문테이블 1차 : 주문일 2차 : 고객번호
- 로그 테이블 1차 : 생성일 2차 : 사용자 ID
- 결제 테이블 1차 : 결제일 2차 : 회원 ID
- 게시글 이력 테이블 

언제 사용하지 않는게 좋을까?
- 데이터가 많지 않을떄
- 단순 CRUD 중심일 떄
- 날짜 조건만으로 충분할떄
- 파티션 관리 경험이 부족할 떄
- 조회 조건이 파티션 기준과 맞지 않을 떄 

파티션의 장점
- 읽어야 하는 데이터 범위를 줄여서 성능을 향상
- 전체 데이터 훼손 가능성 및 감소 및 데이터 가용성 향상
- 각 분할 영역을 독립적으로 백업하고 복구가 가능하다.
- 디스크 스트리핑으로 I/O 성능 향상

// 디스크 스트리핑 : 데이터를 여러 디스크에 나눠서 동시에 저장하거나 읽는 방식

파티셔닝 순서 
- 파티션 종류 결정(범위,분할,조합)
ㄴ 데이터를 어떤 방식으로 나눌지 결정
범위 분할 : 값의 범위로 나눈다.
해시 분할 : 해시 계산 결과로 나눈다.
조합 분할 : 두 가지 방식을 함꼐 사용
- 파티션을 할 키를 설정
ㄴ 데이터를 나눌 기준이 되는 컬럼을 결정
ㄴ 좋은 파티션 키는 데이터를 어느 정도 고르게 나누거나 자주  조회되는 범위를 효과적으로 줄여줄 수 잇어야 한다.
ㄴ 이력 데이터는 생성주기 또는 소멸 주기와 맞춘다.
ㄴ 전체 테이블에서 오래된 데이터를 한 건 씩 삭제한는 것보다 파티션 단위로 관리하는 것이 효율적이다.

- 파티션의 갯수를 결정
- 데이터의 양 : 한 파티션이 너무 커지지 않게 한다.
- 조회 패턴 자주 조회하는 단위와 맞춘다.
- 보관 정책 : 삭제,백업 단위와 맞춤
- 관리 편의성 : 너무 많은 파티션은 피한다.
- I/O분산 : 특정 파티션에 너무 몰리지 않게 한다.
