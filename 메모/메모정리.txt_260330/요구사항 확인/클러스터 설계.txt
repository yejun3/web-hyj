클러스터 설계
- 자주 조회되는 데이터를 디스크의 가까운 위체 모아 저장해서 조회 속도를 높이는 물리적 저장 방법이다.
일반 저장 방식은 책이 아무 책장이나 흩어져 있는 상태
클러스터 저장 방식은 자주 같이 보는 책들은 같은 책작이나 가까운 칸에 모아두는 방식
그렇기 떄문에 조회할 떄는 바르다
하지만 책을 새로 넣거나 위치를 바꾸거나 삭제할 떄는 정리 비용이 더 소모된다.

파티션 : 저장공간을 나눈다.
클러스터 : 관련데이터를 가까이 저장한다.

클러스터 설계 방법
Oracle 기준

CREATE CLUSTER customer_order_cluster(
     customer_id NUMBER
)

customer_id가 같은 데이터끼리 같은 공간에 저장할 창고를 만들어라

클러스터 인덱스를 만든다.
CREATE INDEX idx_customer_order_cluster
on CLUSTER customer_order_cluster;

클러스터 사용하는 테이블을 생성
CREATE TABLE customer(
       customer_id NUMBER PRIMARY KEY,
       customer_name VARCHAR2(50) NOT NULL,
)
CLUSTER customer_order_cluster(customer_id);

CREATE TABLE orders(
    order_id
    customer_id
      ...
)
cluster customer_order_cluster(customer_id);

같은 customer_id를 가진 데이터가 물리적으로 가까운 위치에 저장 될 수 있다.

MySQL
- 오라클 처럼 CREATE CLUSTER를 통해 클러스터를 생성하지는 않는다.
- InnoDB 테이블의  PRIMARY KEY가 자동으로 클러스터형 인덱스가 된다.
- MySQL 공식 문서에서도 InnoDB는 테이블에 primary key를 정의하면 
   그것을 clustered index로 사용한다고 적혀있다.

InnoDB
-MySQL에서 테이블 데이터를 저장하고 관리하는 저장 엔진이다.

PK를 만들면 곧 클러스터가 된다.

적용 기준
분포도가 높을수록 유리한 기법
- 일반적으로 인덱스는 조건으로 조회할 때 데이터가 적을수록 유리하다.
- 그런데 조회범위가 너무 넓으면 인덱스를 타도 많은 행을 계속 찾아가야 해서 오히려 부담이 된다.

select*
from orders
where order_date between '2026-01-01' and '2026-03-31';

- 3개월치 주문 데이터가 매우 많다면 인덱스로 하나하나 찾아가는 비용이 커진다.
- 이런 경우 관련 데이터를 물리적으로 가까이 모아두는 클러스터가 도움이 된다.

클러스터는 액세스 기법이 아니라 물리적 저장방법이다.
select* 
from orders
where customer_id = 10;
- 클러스터는 sql문법에서 직접 "클러스터로 검색해라" 라고 지시하는 개념이 아니다.
- 클러스터는 미리 데이터를 저장할 떄 관련 있는 데이터를 가깝게 저장한다.

분포도가 넓은 테이블은 젖아 공간 절약이 가능하다.
- 클러스터링을 잘하면 같은 기준의 데이터가 모여 저장된다.
customer_id =1인 주문들
customer_id =2인 주문들
customer_id =3인 주문들
- 이렇게 같은 키 값을 가진 데이터들이 모이면, 반복되는 키 관리나 블록 접근 측면에서 저장
효율이 좋아질 수 있다.
- 단, 무조건 저장 공간이 줄어드는 것이 아니다.
- 설계가 잘못되면 오히려 공간 낭비가 생길 수 있다.

작은 테이블
-> 그냥 저체 조회해도 빠름
-> 클러스터 설계효과가 작다

큰 테이블
-> 여러 블록에 데이터가 흩어질 수 있다.
-> 클러스터 설계효과가 커질 수 있다.

- 클러스터는 데이터가 충분히 많고, 조회 패턴이 반복적으로 발생할 때 의미가 있다.

인덱스를 사용한 처리가 부담되는 넓은 분포도에 활용한다.
- 조회할 데이터가 너무 남으면 인덱스에 반복접근이 많아져서 부담된다.
- 클러스터는 관련 데이터를 물리적으로 모아두므로, 넓은 범위를 읽을 떄 블록 접근 수를 줄이는데 도움이 된다.

여러 테이블이 빈번히 조인될 떄 사용

정규화 때문에 분할된 반복 컬럼에 활용한다.

설계 고려사항
- 검색은 빨라지지만 입력,수정,삭제는 느려질 수 있다.
- 새로운 데이터를 넣을떄 어디에 넣어야 같은 그룹끼리 모일까를 고려해야 한다.
- DB는 단순히 빈 공간에 넣는 것이 아니라 , 클러스터 구조를 유지해야 한다.

UNION, DISTINCT, ORDER BY, GROUP BY가 빈번한 컬럼으로 고려한다.
- 이 연산들은 데이터를 묶거나 정렬하거나 중복제거하는 작업이다.

SELECT department_id, COUNT(*)
from employees
group by department_id;

department_id를 기준으로 데이터가 모여있다면 그룹화 작업이 유리할 수 있다.

select*
from orders
order by order_date;

order_date 기준으로 데이터가 어는정도 모여있으면 정렬 부담이 줄어들 수 있다.

하지만 무조건 적용되는 것이 아니다.
해당 컬럼으로 조회, 정렬, 그룹화가 자주 발생하는지 확인해야 한다.
- 클러스터 기준 컬럼은 자주 바뀌지 않는 것이 좋다.
- 회원id -> 거의 바뀔일 없음
반면 status는 자주 바뀔 수 있다.
결제 대기 -> 결제 완료 -> 배송중 -> 배송완료

단일 테이블 클러스터링
- 하나의 테이블 안에서 특정 기준으로  데이터를 모아 저장하는 방식   
- 주문일자 기준으로 모은다.
order 테이블
-> 2026년 1월 주문
-> 2026년 2월 주문
-> 2026년 3월 주문

다중 테이블 클러스트링
- 여러 테이블을 같은 기준으로 묶어서 저장하는 방식
customer_id = 1
-> customer의 고객 1 정보
-> orders의 고객 1의 주문정보

customer_id = 2
-> customer의 고객 2 정보
-> orders의 고객 2의 주문정보

물리 데이터 모델 구성하기
- 논리적으로 설계된 데이터를 실제 데이터 베이스에 저장할 수 있도록 구체적으로 설계하는 작업
- 논리 데이터 모델이 " 어떤 데이터가 필요한가"를 정의하는 단계라면,
- 물리 데이터 모델은 " 그 데이터를 실제 DB에 어떻게 저장할 것인가"를 결정하는 단계
