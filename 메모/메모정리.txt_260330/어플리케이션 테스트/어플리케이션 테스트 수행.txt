어플리케이션 테스트 수행
소프트웨어 개발 생명주기와 V모델
소프트웨어 아키텍트 : 요구사항 분석 및 설계 담당
테스트 매니저 : 검증 및 테스트 담당
둘이 서로 보완관계를 형성한다.

V모델 : 소프트웨어 개발 과정과 테스트 과정을 서로 대응시켜 표현한 모델

요구분석 <-> 인수 테스트 
: 사용자가 요구사항이 실제로 시스템에 제대로 반영되었는지 검증

아키텍처 설계 <-> 시스템 테스트
: 전체 시스템 기능 /비기능 요구사항 및 인터페이스 작동여부 검증

모듈 설계 <-> 통합테스트
: 모듈 간 인터페이스 및 데이터 연동 검증

구현 <-> 단위 테스트
: 기본 단위 컴포넌트 또는 모듈에 로직 검증

---
프로젝트 단계별 테스트 분류 (4가지)
1.단위테스트
- 최소 단위 (모듈 클래스 함수 등)의 소스코드가 설계대로 동작하는지 검증
- 주로 개발자가 구현 직후 작성하여 수행한다.
ㄴ 구조기반 테스트( 화이트 박스 테스트)
ㄴ 명세기반 테스트 (블랙박스 테스트)
2.통합테스트
- 단위 테스트를 통과한 모듈들을 결합하여 모듈간의 인터페이스 및 데이터 흐름의 오류를 검증한다.
ㄴ 빅뱅 , 상향식(Driver), 하향식(Stub), 샌드위치, 중앙식, 협업식, 레이터 통합등의 테스트 방식이 있다.
3.시스템 테스트
- 단위 및 통합을 거친 완제품 형태의 전체 시스템이 기능적, 비기능적 요구사항을 충족하는지 환경 전반에서 검증한다.
ㄴ 명세서 기반의 블랙박스 테스트
ㄴ 성능, 회복, 보안, 부하테스트
4.인수 테스트
- 실제 사용자/고객이 운영 환경이 유사한 조건에서 요구사항 충족 여부를 최종 검증한다.
ㄴ 사용자 인수 테스트
ㄴ 운영상의 인수 테스트
ㄴ 계약 인수 테스트
ㄴ 규정인수 테스트
ㄴ 알파 테스트 
ㄴ 베타 테스트

테스트 기반에 따른 테스트 종류(3가지)
1. 구조기반
- 소프트 웨어 내부의 논리 흐름에 따른 테스트 케이스 작성 및 결함 발견 활동
- 구문 기반 , 결정 기반, 조건 기반, 조건 결정 기반, 변경 조건 기반, 멀티 조건 기반 커버리지
2. 명세 기반
- 사용자의 요구사항 분석서에 주어진 명세를 빠뜨리지 않고 테스트 케이스화
- 동등 분할 , 경계값 분석, 결정 테이블 테스팅, 상태 전의 테스팅, 유스케이스 테스팅
3. 경험 기반
- 유사 소프트웨어나 기술에서의 테스터의 경험, 직관, 기술 능력을 바탕으로 하는 테스트 기법
- 탐색적 테스팅 , 리스크 기반 테스팅

테스트 자동화 도구
테스트 절차를 자동화 도구를 활용하여 준비, 구현, 수행, 분석등을 스크립트 형태로 구현함으로써, 시간과 인력 투입의 부담을 최소화 하면서 운영중인 시스템을 모니터링 하거나 UI가 없는 서비스의 경우에도 정밀한 테스트가 가능하도록 하는 것

장점
-테스트 데이터의 재입력과 재구성 같은 반복 작업을 자동화하여 인력과 시간을 최소화 한다.
- 향상된 요구사항 정의, 성능 및 스트레스 테스트, 품질 측정을 최적화한다.
- 빌드 확인 회귀 , 다중 플랫폼 호환성, 소프트웨어 구성, 기본 테스트 등의 향상된 테스트 품질을 보장한다.

단점
- 테스트 도구 전문가 양성 또는 고용이 필요하며 , 초기에 프로세스 적용에 대한 시간 비용, 노력에 대한 추가 투자가 필요한다.
- 비공개 사용 프로그램의 경우 고가이며  인력과 교육에 대한 유지관리 비용이 비싸다.

---
테스트 자동화 수행 시의 고려사항
- 재사용 및 측정이 불가능한 테스트 프로그램은 제외한다.
- 반복적인 빌드에서  스크립트 재사용성이 가능해야한다.
- 모든 수동 테스트과정을 자동화할 수 없다.
- 도구 환경 설정과 도구 습득 기관을 고려하여 프로젝트 지연을 방지해야한다.
- 테스트 엔지니어를 늦게 투입하면 프로젝트에 대한 이해 부족으로 불완전한 테스트를 초래할 수 있으므로 적절한 투입시기와 계획을 프로젝트 초기에 수립해야 한다.

ㄴ 목적 : 업무흐름별 경로의 적절성, 각 어플리케이션 간 연계 및 연동확인, 기능과 비기능의 적합성 및 사용편의성 확인

ㄴ 테스트 수행 절차 확인: 테스트 관리자 업무 그룹, 기술 지원 등의 역할과  보고 체계를 확인한다.

ㄴ 테스트 시나리오 확인하기
ㄴ 테스트 케이스 확인하기

- 테스트 데이터 확인하기

ㄴ 테스트수행 시 별도의 테스트 데이터가 구성되면 좋으나 만일 실운영 데이터를 사용할 경우에는 특히 데이터의 유지 절차를 고려해야한다.

테스트 관리도구 : 테스트 케이스를 관리 , 테스트 결과 기록, 결함 등록, 결함 담당자 지정, 결함 상태 관리 , 수정 여부를 추적해주는 도구

어플리케이션 결함 관리
결함 
1. 프로그램 명세서 간의 차이 , 업무 내용 불일치
2. 기대 결과와 실제 관찰 결과 간의 차이
3. 시스템이 사용자가 기대하는 타당한 기대치를 만족시키지 못할 때 변경이 필요한 모든 것

결함 관리 프로세스
1. 결함 관리 계획
- 전체 프로세스에서 결함 관리에 대한 일정, 인력, 업무 프로세스를 확보하여 계획을 수립하는 것
2. 결함 기록
- 테스터는 발견된 결함에 대한 정보를 결함 관리 DB에 기록
3. 결함 검토 
- 등록된 결함에 있어서 주요 내용을 검토하고 결함을 수정할 개발자에게 전달한다.
4. 결함 수정 
- 개발자는 할당된 결함의 프로그램을 수정한다.
5. 결함 재확인 
- 테스터는 개발자가 수정한 내용을 확인하고 다시 테스트를 수행한다.
6. 결함 상태 추적 및 모니터링 활동
- 결함 관리 팀장은 결함 관리 데이터베이스를 이용하여 대시보드 또는 게시판 형태의 서비스를 제공한다.
7. 최종 결함 분석 및 보고서 작성
- 발견된 결함에 대한 내용과 이해관계자 간의 의견이 반영된 보고서를 작성하고 결함 관리를 종료한다.

결함의 상태 및 추적
결함은 여러 상태를 가지고 있으며 이 상태의 변화를 지속적으로 추적 관리하는 것이 결함 관리의 주요 작업 중 하나이다.

1. 결함 등록(Open)
-테스터와 품질 관리 담당자에 의해 결함이 처음 발견되어 등록되었지만, 아직 분석되지 않은 상태
2. 결함 검토(Review)
- 등록된 결함을 담당 모듈 개발자, 테스터, 프로그램 리더, 품질 관리 담당자와 검토하는 상태
3. 결합 할당(Assigned)
- 결함의 영향 분석 및 수정을 위해 개발자와 문제 해결 담당자에게 할당된 상태이다.
4. 결함 수정(Resolved)
- 개발자에 의해 결함의 수정이 완료된 상태이다.
5. 결함 조치 보류(Deferred)
- 수정이 필요한 결함이지만 현재 수정이 불가능해서 연기된 상태로서 우선순위 , 일정 등을 고려하여 재오픈을 준비하는 상태
6. 결함 종료(Closed)
- 발견된 결함이 해결되고 테스터와 품질고나리 담당자에 의해 종료 승인을 한 상태이다.
7. 결함 해제(Clarified)
- 테스터, 프로그램 리더, 품질 관리 담당자가 결함을 검토한 결과 , 결함이 아니라고 판명된 경우

--
결함의 분류(4가지)
시스템 결함
- 비정상적인 종료/중단
- 응답시간 지연
- 데이터베이스 에러

기능 결함 
- 요구사항 미반영/불일치
- 부정확한 비즈니스 프로세스
- 스크립트 에러 
- 타 시스템 연동 시 오류

GUI 결함
- 응용 프로그램 UI 비일관성
- 부정확한 커서/메시지
- 데이터 타입의 표시 오류

문서결함
- 기획자, 사용자, 개발자 간의 의사소통과 기록이 원할하지 않은 경우에 발생하는 결함
- 사용자의 온라인/오프라인 메뉴얼 불일치
- 요구사항 분석서와 기능 요구사항의 불일치로 인한 불완전한 상태의 문서

-----
결함 심각도 
- 여러개의 결함 중 전체 시스템에 결함이 미치는 영향을 레벨별로 나타내는 것

High
-시스템이 중단되어 더이상 프로세스를 진행할수 없게 만드는 결함
- 핵심 요구사항 미구현, 시스템 다운, 장시간 시스템 응답 지연, 시스템 복구 후 데이터 왜곡

Medium
- 시스템의 흐름에 영향을 미치는 결함
- 부정확한 기능, 부정확한 업무 프로세스, 데이터 필드 형식 오류, 데이터베이스 에러, 보안 관련 오류

Low
- 시스템의 흐름에는 영향을 미치지 않는 결함이나 상황에 맞지 않는 용도와 화면 구성의 결함
- 부정확한 GUI 및 메시지, 에러 시 메시지 미출력, 화면상의 문법/철자오류

분석 : 요구사항의 표준 미준수, 테스트 불가능, 불명확

발생한 결함에 대한 결함 상태를 정의
Open : 결함이 보고되었지만 아직 분석되지 않은 상태
Assigned : 결함을 개발자에게 할당한 상태
Fixed : 개발자가 결함을 수정한 상태
Closed : 결함이 수정되었는지 확인하고 회귀 테스트시 결함이 발견되지 않은 상태(수정된 결과가 만족스럽지 않을 경우, 결함의 상태를 open으로 변경한다.)
Defferred : 결함 우선순위가 낮게 분류되었기 때문에 결함수정을 연기한 상태
Clarified : 보고된 결함이 프로젝트 팀에 의해 결함이 아니라고 판단된 상태

정의한 결함 유형을 이용하여 결함관리 현황을 결함관리 표에 결함상태를 같이 작성한다.

ㅡMock 테스트
ㄴ 단위 테스트시 Mock 객체를 사용하여 테스트하는 기법

ㄴ 이를 체계적으로 구체화시켜 테스트케이스을 도출하고 작성하는 것을 테스트 구현이라고 하고 , 테스트 상황과 방법을 구체화시키기 위한 수단 및 도구를 테스트 설계 방법이라고 한다.
- 테스트 설계 방법
보다 작은 케이스 
ㄴ 동등 클래스 (동등 분할기법)
보다 많은 버그 찾기

ㄴ 상태 전이 테스트, 모든 테스트 요소를 매트릭스 형태로 나열하여 테스트

ㄴ 동시 접속으로 시스템의 많은 요청이 발생될 때 어떻게 가동되는지 확인하는 테스트
ㄴ 성능 요구사항에 정의된 임계점을 넘어 부하가 계속 증가하는 상황에서 시스템이 정상적인 수준의 반응을 보이는지 확인해야한다.
- 장애 복구 테스트
ㄴ 각종 장애 상황에서 복구 및 재가동을 테스트한다.
ㄴ 어플리케이션 장애 복구 테스트는 다양한 관점에서 테스트할 수 있으나 , 서비스의 지속적인 유지라는 측면에서 발생할 수 있는 장애를 목록으로 작성하고 장애 상황을 발생시킨다.
ㄴ 시스템 장애와 어플리케이션 장애로 나눌 때 시스템 장애는 인프라 아키텍처 팀 등에서 별도로 담당하여 진행하도록 하고, 소프트웨어 아키텍트는 어플리케이션 장애 관점에서 복구 테스트를 수행 하도록 한다.

- 보안 테스트
ㄴ 별도의 보안 전문가에 의해 어플리케이션 전반에 걸쳐 검증받는 것이 바람직하다.
ㄴ 보안성 검증은 어플리케이션의 기능적 요구사항과는 별도로 해킹이나 침투에 대비할 수 있는 최신 기술 트렌드가 반영된 검증이 필요하다.
ㄴ 보안 검증이 완료되면 결과를 바탕으로 취약점 분석을 한 후  개선방안을 수립하고 반드시 이를 시스템에 반영하도록 계획을 수립해야 한다.
1-4 인수 테스트 기법
- 최종 사용자가 요구한 기능이 제대로 반영되었는지 , 인수 조건에 만족하는지를 테스트하는 기법이다.
- 요구사항 기능 만족 여부, 사용 편리성에 대하여 실제 운영 환경에서 실행되며 고객이 주도하는 테스트이다.

2. 결함 관리의 이해 
2-1 결함 관리 용어
- 에러 (Error)
ㄴ 소프트웨어 개발 또는 유지 보수 수행 중에 발생한 부정확한 결과로 , 개발자의 실수로 발생한 오타 , 개발 명세서의 잘못된 이해, 서브루틴의 기능 오해가 있다.
- 오류 (Fault)
ㄴ 프로그램 코드상에 존재하는 것으로 비정상적인 프로그램과 정상적인 프로그램 버전 간의 차이로 인하여 발생되며 , 잘못된 연산자가 사용된 경우에 프로그램이 서브루틴으로 부터 에러 리턴을 점검하는 코드가 누락된 것

-실패 (Failure)
ㄴ 정상적인 프로그램과 비정상적인 프로그램 실행 결과의 차이를 의미하며 실행 중에 프로그램의 실제 결과를 개발 명세서에 정의된 예상 결과와 비교함으로써 발견한다.
- 결함(Defect)
ㄴ 버그,에러, 오류, 실패, 프로그램 싱행에 대한 문제점, 프로그램 개선 사항등의 전체를 포괄하는 용어
2-2 결함 판단의 기준
- 기능 명세서에 가능하다고 명시된 동작을 수행하지 않는 경우
- 기능 명세서에 불가능하다고 명식된 동작을 수행하는 경우
- 기능 명세서에 명시되어 있지않지만 수행해야할 동작을 수행하지 않는 경우
- 테스터의 시각에 볼 때 문제가  있다고 판단되는 경우

테스터의 시각에서 결함으로 판단되는 경우
이해하기 어려움 기능, 사용이 까다로운기능, 비정상적으로 사용이 느린 기능

3, 테스트 경언 
3-1 소프트웨어를 완벽하게 테스트하는 것은 불가능하다.
- 가능한 입력의 수가 많아
- 가능한 출력의 수가 너무 많다.
- 소프트웨어 명세서가 주관적이다.
- 소프트웨어 결합도 주관이다.
3-2 소프트웨어 테스트는 위험을 수반하는 훈련이다.
- 가능한 한 모든 테스트 시나리오와 테스트 케이스를 테스트하지 않을 경우 위험을 감수하기로 했다는 뜻과 같다.
- 테스터는 무엇이 중요하고 중요하지 않는지 혐명한 판단을 하여야한다.
3-3 테스트 작업으로 결함이 본재하지 않는다는 사실을 입증할 수 없다.
- 테스트를 통해 소프트 웨어 결함이 o가 없다는 것을 보장할 수는 없으며 단지 테스트 결과로 결함이 있다는 사실만을 보여줄 수 없다.
3-4 아래와 같은 이유로 사유로 인하여 발견한 모든 결함을 수정할 수는 없다.
-쫓기는 작업일정
- 외부적 요인으로 결함이 아님에도 결함으로 판단되는 경우
- 각각의 프로그램 간에 서로 결합도가 높은 경우의 고치기 위험한 결함
- 현실에서 거의 발생할 가능성이 없는 경우의 고칠 가치가 없는 결함 
3-5 발견한 결함이 많을수록 남아있는 결함의 수도 많다.

4. 소프트 웨어 테스터의 역할과 능력
4-1 소프트웨어 테스터의 역할
- 가능한 결함을 빨리 발견하여 결함이 수정, 보완되었는지 확인하는 것 
4-2 소프트웨어 테스터의 능력
- 탐구심과 문제 해결력을 갖춰야한다.
- 때로는 창의력을 발휘하여 결함을 찾기 위해 새로운 접근법도 사용해야 한다.
- 완벽함을 추구하지만 가능한 한도 내에서 적당한 수준의 완벽성을 추구한다.
- 테스터는 항상 나쁜 소식을 전하는 사람이다. 개발자에게 결함이 있다고 말해야한다.
